## CRITICAL

**[CRITICAL] The admin console's product-edit "Reject" action is broken in production by this commit.** — `packages/shared/src/schemas/admin/products.ts:80-90` narrows `decision` to `'approve' | 'request_changes'` and adds `.refine(notes required when request_changes)`, but every caller still sends `'reject'` with no notes: `apps/admin/src/app/(admin)/products/pending/pending-actions.tsx:22` → `apps/admin/src/lib/actions.ts:36-42` → `apps/admin/src/lib/admin-api.ts:86-89` → `PATCH /v1/admin/products/pending/:id`, which parses the schema at `api/src/routes/admin/products/pending-resolve.ts:12`. Every reject now returns 400 `validation_error`. This passes CI because (a) the admin call sites use hand-written string-literal unions, not the inferred shared type, so `apps/admin` typecheck stays green, and (b) the only API test for this route sends `decision: 'approve'` (`api/tests/integration/admin/products.test.ts:103`) — there is no negative/reject case. Naive fix is also broken: renaming the admin literal to `request_changes` without adding notes still 400s on the new `.refine`. — **Recommendation:** in the same PR as this contract change, update the three admin call sites to send `request_changes` **plus** a notes string (prompt or default), or temporarily accept `'reject'` as an alias in `adminProductEditResolveSchema` and add an API test for the non-approve branch. The phase file mandated the rename; it did not authorize leaving the only caller broken for 5 phases.

## IMPORTANT

**[IMPORTANT] `request_changes` still writes the terminal `rejected` state.** — `api/src/routes/admin/products/pending-resolve.ts:24`: `status: input.decision === 'approve' ? 'approved' : 'rejected'`. Phase file requirement (line 27) is explicit: "Admin action is named `request_changes`; resulting state is `changes_required`… The only new write to `rejected` is an explicit stale-revision `supersede`". So once CRITICAL-1 is fixed, the first request-changes action writes an irreversible, read-only-by-spec `rejected` row instead of a resumable `changes_required` one. The enum value `changes_required` exists in the DB (migration A1) and in `productEditStatusSchema`, so nothing but the route stands in the way. — **Recommendation:** map `request_changes → changes_required` and persist `moderationNotes` (the new column) rather than the legacy `notes` column, or explicitly defer with a code-level guard that rejects `request_changes` with `501/upgrade_required` until Phase 4 owns the writer. Do not leave the accepted input silently producing the wrong terminal state.

**[IMPORTANT] Product-level moderation notes are exposed to every caller in the public product DTO.** — `api/src/services/products/serializer.ts:39` maps `moderationFeedback: p.moderationNotes` unconditionally, and `moderationFeedback` is a required field of the *public* `productSchema` (`packages/shared/src/schemas/product.ts:95`). `toApiProduct` feeds four public routes: `routes/products/get.ts:23` (any authenticated user, any product id), `routes/products/lookup.ts:32`, `routes/products/search.ts:17`, `routes/products/create.ts:27`; it is also embedded in `problemSchema.canonicalProduct` (`packages/shared/src/schemas/error.ts:21`), so it rides along in `version_conflict` problems too. The behaviour is asserted as intended in `api/tests/unit/products-serializer.test.ts:66-72` (`expect(api.moderationFeedback).toBe('Blurry cover photo')`). This contradicts the phase's own success criterion "Public DTOs never expose storage keys/uploader/moderation internals" (phase file line 203). Exposure is currently *latent* — `products.moderation_notes` is new in migration A2 and no writer exists yet — but the leaking shape is now baked into the shared contract and the vendored mobile dist, and Phase 4 will start populating the column. — **Recommendation:** remove `moderationFeedback` from `productSchema` and surface it only on creator-private projections (`productDraftRowSchema` already carries it), or pass an explicit `viewerIsCreator`/`includeModerationFeedback` argument into `toApiProduct` and default it to omitted. Add a serializer test asserting a non-creator projection contains no `moderationFeedback`.

**[IMPORTANT] `productDraftPatchRequestSchema` converts an omitted `description` into an explicit `null` — silent data loss on partial patches.** — `packages/shared/src/schemas/product.ts:40-56` (`productDescriptionSchema` = `.nullable().optional().transform(...)`) and `:229` use it directly as the object field. Verified with the repo's own zod build: `parse({ name: 'x' })` → `{"name":"x","description":null}`; `parse({})` → `{"description":null}`; `'description' in parsed === true`. Consequences: (1) a Phase 2 handler that spreads the parsed patch into a Prisma update — the pattern used at `api/src/routes/products/patch.ts:33` — wipes an existing description whenever the client patches only `name`; (2) the existing empty-payload guard idiom (`Object.keys(input).length === 0`, `patch.ts:13`) can never trigger, so an empty `{}` body becomes a destructive write. No test covers the omitted-key case (`packages/shared/src/schemas/product.test.ts:282-292` only tests a supplied description). — **Recommendation:** split the schema: keep a `productDescriptionValueSchema` (`string | null` → normalized) for required-value contexts and use `productDescriptionValueSchema.optional()` inside the patch object so an omitted key stays `undefined`. Add tests for omitted key, explicit `null`, and `{}`.

**[IMPORTANT] The one-open-edit invariant fails open: `is_legacy` defaults to `true`.** — `api/prisma/migrations/20260726160100_.../migration.sql` adds `"is_legacy" BOOLEAN NOT NULL DEFAULT true` and the partial unique index is `WHERE (NOT "is_legacy" AND status = ANY(...))`; `api/prisma/schema.prisma` mirrors it with `@default(true)`. The default that *disables* the constraint applies to every future insert, not just the backfill. The live writer `api/src/routes/products/patch.ts:29-35` creates `ProductEdit` rows without `isLegacy`, so every edit it creates is exempt and one user can open unlimited concurrent `pending` edits on one product. The integration tests only prove the constraint when `isLegacy: false` is passed explicitly (`api/tests/integration/products-schema.test.ts:389, 413, 424`), so the gap is invisible. Phase success criterion "Database enforces … one-open-edit race invariants" is therefore only met for writers that remember to opt in. — **Recommendation:** follow-up migration doing `ALTER TABLE product_edits ALTER COLUMN is_legacy SET DEFAULT false` (backfill already done) plus `@default(false)` in Prisma, so omission fails closed; set `isLegacy: false` in `patch.ts`. Add a test that inserts two open edits **without** specifying `isLegacy` and expects the second to fail.

**[IMPORTANT] Migration B's preflight implements one of the three mandated aborts.** — `api/prisma/migrations/20260730040000_classify_report_hidden_products/migration.sql` only aborts on `status='pending' AND submitted_at IS NOT NULL`. Phase file line 166 requires abort "if creation mode is not `off`, any submission timestamp/private draft lifecycle marker exists on such a row, or any deployed report writer still emits `pending`". The creation-mode precondition **is** DB-checkable — migration A2 inserts `settings('product_creation','{"mode":"off"}')` — so the file's comment ("the one precondition that IS DB-checkable") is factually wrong. Other DB-checkable markers on a candidate row are also unchecked: `moderated_at`/`moderated_by_user_id`, `version > 1`, any `product_photos` row, any non-legacy `product_edits` row. Failure mode is silent, irreversible data corruption: a creator-submitted `pending` product flipped to `report_hidden` disappears from its creator's drafts with no audit trail. — **Recommendation:** extend the `DO` block to also `RAISE EXCEPTION` when `(SELECT value->>'mode' FROM settings WHERE key='product_creation') IS DISTINCT FROM 'off'` and when any candidate row carries a lifecycle marker; add integration cases for each new abort next to `api/tests/integration/products-schema.test.ts:471`.

## MODERATE

**[MODERATE] Photo reorder cannot be expressed as an `UPDATE` — the position constraints leave no legal intermediate state.** — `product_photos_product_id_position_key` is a plain (immediate, non-`DEFERRABLE`) UNIQUE and `product_photos_position_check` pins `position` to 0–4; `product_edit_photos` has the same pair. Verified empirically in rolled-back transactions against `pantry_test`: a single-statement swap `UPDATE product_photos SET position = CASE position WHEN 0 THEN 1 ELSE 0 END WHERE product_id = …` fails with SQLSTATE **23505**, `Key (product_id, "position")=(…, 1) already exists`; and the usual escape hatch `UPDATE … SET position = 5` fails `violates check constraint "product_photos_position_check"`. The plan promises a "transactional contiguous-order rewrite" (plan.md risk table) and Phase 1 owns these constraints. — **Recommendation:** decide now and record it in the Phase 2/3 phase files: either make the unique constraints `DEFERRABLE INITIALLY IMMEDIATE` (+ `SET CONSTRAINTS … DEFERRED` in the reorder transaction) or mandate delete-then-reinsert of the whole ordered set. Discovering this inside Phase 3 will cost a migration.

**[MODERATE] The serializer never orders `photos` by `position`.** — `api/src/services/products/serializer.ts:40` maps `p.photos ?? []` in whatever order the Prisma include returned; Prisma applies no default `orderBy`, so row order is unspecified. `position 0 = cover` is contractual (plan.md Global Constraints). The test at `api/tests/unit/products-serializer.test.ts:104-110` only proves array order is preserved, not that it is correct. — **Recommendation:** sort by `position` inside `toApiProduct` so no caller can get cover order wrong.

**[MODERATE] `productSchema.photos` is looser than the DB and the spec.** — `packages/shared/src/schemas/product.ts:97` is `z.array(productPhotoSchema)` with no `.max(5)` and no unique-position rule, while the DB enforces `position 0..4` + `UNIQUE(product_id, position)` and the plan caps at five ordered photos. A buggy or malicious writer can emit six photos or duplicate positions and the response contract will accept it. — **Recommendation:** `.max(5)` plus a `superRefine` for unique positions.

**[MODERATE] The Phase 1 "compatibility reader" step is unimplemented and untested.** — Phase file line 165 requires that legacy `pending` and new `report_hidden` rows be "treated as hidden by every Phase 1-touched serializer/consumer". `api/src/services/products/lookup.ts:17-23` (`findUnique` on `barcode`/`qrPayload`) and `api/src/routes/products/get.ts:13` (`findUnique` by id) apply no status filter, so `report_hidden`, `draft`, and `pending` rows serialize fully to any authenticated caller; only `services/products/search.ts:40` filters `status = 'active'`. This is **not a regression** (legacy `pending` already behaved this way and neither file is touched by the commit) and plan.md assigns "active-only legacy lookup" to Phase 2 — but nothing in Phase 1 asserts the hidden-ness the rollout gate depends on. — **Recommendation:** treat this as a Phase 2 blocking item that must land *before* the report-writer switch to `report_hidden`, with a test proving `report_hidden` is invisible via `/v1/products/lookup` and `/v1/products/:id`.

**[MODERATE] A `rejected` photo can never have its storage key cleared.** — `product_photos_storage_and_moderation_check` requires `private_storage_key IS NOT NULL` for `pending|rejected`. A cleanup worker that deletes rejected private bytes cannot null the key afterwards without violating the check, so a swept row would permanently reference a nonexistent object. — **Recommendation:** document in Phase 3/7 that rejected-photo cleanup deletes the **row** (and enqueues `delete_private`), never just the key.

**[MODERATE] Admin↔API deploy order is now coupled and undocumented.** — `adminProductEditRowSchema` gained six required fields (`version`, `baseProductVersion`, `moderationNotes`, `submittedAt`, `resolvedBy`, `resolvedAt`, `packages/shared/src/schemas/admin/products.ts:69-77`) and `apps/admin/src/lib/admin-api.ts:83-85` parses `adminProductEditsListSchema` on every `/admin/products/pending` render. An admin build carrying the new shared package against an API instance predating this commit throws on the pending page. Verified this is the *only* such coupling: no other `apps/admin`/`apps/mobile` source parses `productSchema`, `productWithReviewsSchema`, `productLookupResponseSchema`, or `productSearchResultSchema`, so the new required product fields break no existing client. — **Recommendation:** add "deploy API before admin" to the plan's Rollout Strategy step 2.

**[MODERATE] Uploader FKs are `RESTRICT` while the product creator FK is `SET NULL`.** — `product_photos.uploaded_by_user_id` and `product_edit_photos.uploaded_by_user_id` are `ON DELETE RESTRICT` (migration A2; `schema.prisma`), whereas `products.created_by_user_id` is `SET NULL`. No hard-delete path exists today (verified: no `prisma.user.delete` anywhere in `api/src` or `apps/admin/src`; admin user routes are get/list/patch/impersonate/revoke-sessions only), so nothing is broken now — but any future account-erasure/GDPR path will be blocked by a photo upload. — **Recommendation:** Phase 7 should decide `SET NULL` + retained-uploader audit vs. an explicit erasure procedure, and record it.

**[MODERATE] `api/prisma/schema.prisma` carries a whole-file `prisma format` reflow beyond the phase's scope.** — 162 whitespace-normalized diff lines touch `User`, `Record`, `Review`, `ReviewVote`, `ApiError`, `Deal`, `DealVote` — models this phase does not own. I verified the reflow is semantically inert (whitespace-normalized sorted diff yields only `@db.Uuid @map(...)` → `@map(...) @db.Uuid` attribute reorderings; no type, default, index, or relation change), so there is no correctness finding — but it violates `.claude/rules/development-rules.md` "keep changes scoped" and inflated the surface a reviewer must clear. — **Recommendation:** none required retroactively; avoid whole-file formatters on shared schema files in later phases.
